# V0 계약 공시 Vertical Slice

## 스키마 설계안

V0는 외부 서비스 없이 재현 가능한 SQLite를 사용한다. SQL은 PostgreSQL 이관을 쉽게 하기 위해 자연키인 접수번호를 `TEXT` primary key로 유지하고, 금액과 비율은 `NUMERIC`, 날짜는 ISO `YYYY-MM-DD` 문자열로 저장한다. PostgreSQL 이전 시 날짜 열은 `DATE`, 정수형 boolean은 `BOOLEAN`, 자동 증가 기업 ID는 `BIGINT GENERATED BY DEFAULT AS IDENTITY`로 바꾸면 된다.

| 테이블 | 역할 | 핵심 설계 |
|---|---|---|
| `companies` | 기업 식별 | `corp_code` 우선 식별, 표시 기업명 보존 |
| `disclosures` | 공시 접수 이벤트 | 접수번호, 공시일, 보고서명, 정정 여부, raw XML 경로와 SHA-256 |
| `contracts` | 계약 필드 | 정규화 값, `_raw` 원문, `_source` 행/셀 위치를 필드마다 병렬 저장 |
| `correction_links` | 확정 정정 관계 | phase2의 `explicit_original_filing_date` + `high`만 허용. candidate는 저장하지 않음 |

`correction_links.original_receipt_no → correction_receipt_no`는 방향성 edge다. 최신 유효 필드는 명시 edge로 구성된 chain을 시간순으로 순회하면서 각 필드의 마지막 non-null 값을 overlay한다. 따라서 정정문에서 변경하지 않은 필드가 비어 있어도 원공시 값을 유지한다.

## 범위

- 입력은 1차 `document_manifest.csv`, phase2 `correction_chains.csv`, 원본 `data`의 exchange XML이다.
- 보고서명이 `단일판매ㆍ공급계약`을 포함하는 접수만 처리한다.
- periodic, holding, major, 신규시설투자, 일반 투자판단 공시는 처리하지 않는다.
- 원본 XML은 읽기만 하며 변경·이동·삭제하지 않는다.
- RAG, 임베딩, Vector DB는 포함하지 않는다.

## 추출 방식

HTML 표의 `TR` 단위로 셀을 읽고 다음 라벨을 매핑한다.

- `계약금액(원)` → 정수 금액
- `계약상대`, `계약상대방` → 상대방 문자열
- `시작일`, `종료일` → ISO 날짜
- `매출액대비(%)`, `매출액 대비(%)` → 소수 비율

정정표의 `정정전/정정후` 행은 본문 양식 표보다 앞에 나타난다. 같은 필드 후보가 여러 번 나오면 정정 후 값 또는 뒤쪽 본문 양식 값을 우선하며, `-`, 미정, 유보 등은 정규화 값 null로 보존하되 raw 문자열은 유지한다.

## 실행 방법

```powershell
python src/ingest_contracts.py --db artifacts/v0_contracts.sqlite
python src/query_contracts.py list --db artifacts/v0_contracts.sqlite --company 현대건설 --year 2025
python src/query_contracts.py latest --db artifacts/v0_contracts.sqlite --company 현대건설 --receipt-no <접수번호>
python src/validate_contracts.py --db artifacts/v0_contracts.sqlite --sample-size 10
python -m unittest tests.test_contract_ingestion
```

## 최신값의 한계

phase2의 similarity candidate는 최신값 계산에서 사용하지 않는다. 명시 chain이 없는 정정공시는 독립 접수로 조회되며, 데이터 범위 밖 원공시를 자동 생성하지 않는다. “최신”은 현재 로컬 데이터 안에서 명시적으로 연결된 마지막 관측값이라는 뜻이지 법적 최종 상태를 보증하지 않는다.

## 실행 검증 결과

`artifacts/v0_contracts.sqlite`를 실제 원본으로 생성하고 전체 테스트를 수행했다.

| 지표 | 결과 |
|---|---:|
| 기업 | 33 |
| 계약 공시 접수 | 1,126 |
| 계약 레코드 | 1,126 |
| 명시 정정 링크 | 287 |
| similarity candidate 적재 | 0 |

정규화 값과 raw 값의 누락률은 구분한다. 예를 들어 계약금액 raw가 `-` 또는 공시유보 상태면 raw는 존재하지만 정규화 금액은 null이다.

| 필드 | 정규화 누락률 | raw 누락률 |
|---|---:|---:|
| contract_amount | 9.68% | 1.78% |
| counterparty | 3.02% | 0.00% |
| contract_start_date | 11.10% | 0.00% |
| contract_end_date | 19.01% | 0.00% |
| sales_ratio | 5.86% | 0.00% |

검증 스크립트는 명시 chain을 기준으로 최신값 샘플 10개를 출력한다. 단위 테스트 5개는 적재 범위, raw/source 보존, candidate 배제, 명시 chain 해석, 필수 출력 필드를 검증하며 모두 통과했다.

## 구현 파일

- `src/db/schema.sql`: SQLite/PostgreSQL 이관 친화 스키마
- `src/contract_core.py`: XML 표 추출, 정규화, 명시 chain과 field overlay
- `src/ingest_contracts.py`: 재현 가능한 전체 ingestion
- `src/query_contracts.py`: 기업·연도 목록과 특정 접수의 최신값 CLI
- `src/validate_contracts.py`: 건수, 누락률, 링크 수, 최신값 샘플 검증
- `tests/test_contract_ingestion.py`: 격리된 임시 DB 기반 테스트
